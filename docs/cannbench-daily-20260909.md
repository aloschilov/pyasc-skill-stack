## Методика и границы интерпретации

- Runtime/source pyasc v2 закреплены на `adadd7d66ed0ee16d33d79487bf584899a26ef1e`; evaluator ref из снимков runner: `e8609f6b5891361fb6f0afb141eb8909c1b4a59b`. Аппаратный pool — 950PR.
- Во всех снимках `is_independent_environment=false`. Первые четыре варианта и c64 выполнялись на runner-950pr-host2, JIT и inline-Erf — на runner-950pr-multi #2. Имя runner — наблюдаемый фактор, не измерение частоты, загрузки или троттлинга.
- `NPU µs` — сохранённое `elapsed_us` официального case; `Ref µs` — `baseline_perf_us`, не время предыдущего нашего ядра и не теоретический hardware limit. Время загрузки/компиляции сюда не добавлялось; отчёт не переизмеряет ядра.
- `speedup = Ref µs / NPU µs`. Независимый GM = exp(mean(log(speedup))) по 20 корректным cases с равным весом. Значение <1 означает медленнее reference. Для comparisons previous/new используются задержки двух наших jobs с совпадающим case.
- Score и поля API `geometric_mean_speedup`/`geometric_mean_speedup_vs_hw` сохраняются отдельно ниже. Их значения не совпадают с прямым GM по 20 case speedups; без проверки серверной агрегации нельзя подменять ими независимый показатель.
- `tile_shape=[N]` относится к плоскому представлению входа, а не к исходной строке. `AIV зап./пол.` — число запущенных векторных workgroups и аналитически вычисленных непустых разбиений. Это **не количество одновременно занятых физических AI Core** и не AIC matrix cores.
- Локальная конфигурация CANN для 950PR_9589 указывает 64 AIV/32 AIC, для 9599 — 72/36; это конфигурационные данные, не live telemetry. Именно эту неоднозначность проверяет c64; запуск 72 workgroups не утверждает наличие 72 физических AIV.
- UB — статическое потребление на специализацию по компилятору; бюджет 248 KiB (253952 B). В таблицах указаны KiB и доля бюджета. Заполнение UB не является самостоятельной целью: память могут занимать лишние промежуточные тензоры.
- Общее для всех строк: `static_alloc=None` (эффективно True), `insert_sync=True`, `opt_level=3`, `debug=False`; vf_vec_len оставлен платформенным. `reuse_alloc` и VF в таблице — эффективный выбранный маршрут, включая launch override, а не только текст декоратора. `always_compile`/`verify_sync` диагностических проб не следует переносить на эти timings.
- Во всех вариантах FP16/BF16 вычисляют через FP32 и приводят результат к dtype входа. Exact (`none`) и tanh — разные математические маршруты. В высокоуровневых вариантах FP32 exact использует уже принятую коррекцию хвоста, в inline-диагностике она удалена.
- Один job на вариант, без повторных независимых hardware-измерений и доверительных интервалов. Изменения на 1–4% не следует объявлять статистически устойчивыми.
- Ссылки на jobs ведут в workspace CANNBench и могут требовать авторизации владельца. Этот файл самодостаточен для чтения: все cases, конфигурации, исходники GeLU и SHA256 встроены; приватные ответы API, ключи, временные URL скачивания и wheels не публикуются.

## Локальная квалификация и смысл диагностики

До отправки геометрических вариантов проверены неизменность математики/source gate, замороженные source/runtime/package hashes, 20 официальных host/IR/translation специализаций через x86/QEMU и 108 проверок разбиения (20 official + 108 edge в журнале gate). QEMU-проверка не является исполнением численного ядра на NPU. CaModel выполнял уменьшенные численные, tail, idle, guard и repeat-наборы; они не заменяют полные официальные shapes.

У tile3840 и tile3840_jit пять неизменённых dtype/mode маршрутов наследовали предыдущую численную квалификацию, изменённый FP32 exact квалифицировался отдельно. balanced5120 и balanced3840 имеют по 18 численных/tail/idle проверок шести маршрутов. c64 наследует 18 проверок balanced3840 после gate на изменение только cap и добавляет шесть реальных 64-block tail/repeat/guard проверок и один tiny-tile stress.

Локальная JIT-матрица включала 36 fresh-process compile probes: две геометрии × reuse 0/1/2 × static None/False/True × VF False/True. Для static=False отсутствовала ожидаемая UB-метадата; это ограничение допуска к Model в интеграции, не доказательство неработоспособного JIT-флага. Не все комбинации были замерены на hardware. Отключение синхронизации не использовалось.

Для inline SUBSECTION: восемь из девяти exact-проверок прошли; seeded FP32 negative-tail остаётся невалидным: cancellation errors 7 против CPU 2, отношение 3,5 при допустимом ≤2. Шесть tanh-проверок унаследованы после проверки идентичности AST. Пройдено 20/20 QEMU-специализаций и 16 уменьшенных official-range проверок. На 4096 аргументах primitive Erf SUBSECTION показал максимум 1 ULP, direct/default PADE — 5 ULP; это выборочный результат, не глобальная гарантия.

При локальном matched Model-сравнении на 15360 FP32 элементах в [-2,2], tile5120/u1, один блок: SUBSECTION median 14068 ticks, stable-tail 20450 ticks (1,4537× относительно нашего workaround, не относительно CANNBench reference). Эти локальные данные оправдывали один диагностический submission, но не обещали hardware speedup.

Официальные 20/20 inline не опровергают отдельный adversarial failure: отличаются входные выборки и область проверки. Для production точность в отрицательном хвосте остаётся открытой. [Публичный контекст запроса ErfConfig: pyasc issue #8](https://gitcode.com/compiler-team/pyasc/issues/8).

### Исходник baseline5120

[Назад к результатам](#run-baseline5120). SHA256: `1d5220eee6e26f3f377eb7ec75be5fcec8c2bfebda4d347b728686b6434dca86`. Wheel submission SHA256: `ffad9499f47ab03abe5b16d52ba4a6bf655c005bb3843d78fd74b63624c98ad3`.

```python
"""Public AscTile GeLU, corrected target tanh and stable FP32 exact tail.

Pinned runtime: adadd7d66ed0ee16d33d79487bf584899a26ef1e.
No inline AscendC or compiler modifications. See EXACT_REMEDY.md.
"""
import asctile
import torch

from ._pyasc_runtime import ensure_npu_platform


def geometry(is_fp32: bool, approximate: str):
    if approximate == 'none' and is_fp32:
        return 5120, 1, True
    if approximate == 'tanh' and is_fp32:
        return 15872, 2, False
    return 8192, 2, False


@asctile.jit(reuse_alloc=1)
def gelu_kernel(input_ptr: asctile.GlobalAddress, output_ptr: asctile.GlobalAddress,
                input_length, tile_length: asctile.ConstExpr,
                unroll_factor: asctile.ConstExpr, approximate: asctile.ConstExpr,
                stable_tail: asctile.ConstExpr):
    in_gm = asctile.global_tensor(input_ptr, [input_length])
    out_gm = asctile.global_tensor(output_ptr, [input_length])
    block_loop_num = asctile.ceildiv(asctile.ceildiv(input_length, asctile.block_num()), tile_length)
    block_length = tile_length * block_loop_num
    block_offset = block_length * asctile.block_idx()
    # Do not issue zero-length DMA for the unused end of a core's partition.
    local_tiles = min(block_loop_num, asctile.ceildiv(max(0, input_length - block_offset), tile_length))
    for i in asctile.range(local_tiles, unroll_factor=unroll_factor):
        offset = block_offset + i * tile_length
        valid = max(0, min(input_length - offset, tile_length))
        raw = asctile.copy_in(in_gm, [offset], [tile_length], real_shape=[valid], pad_value=0)
        x = raw.to(asctile.float32)
        if approximate:
            square = x * x
            cube = square * x
            exponent = (x + cube * 0.044715) * -1.5957691216057308
            out = x / (asctile.exp(exponent) + 1.0)
        else:
            out = (x * 0.5) * (asctile.erf(x * 0.7071067811865476) + 1.0)
            if stable_tail:
                # Normal-tail Mills ratio (DLMF 7.9.1), six levels for a >= 3.
                a = asctile.maximum(-x, 3.0)
                remainder = asctile.full([tile_length], 0.0, asctile.float32)
                for order in asctile.static_range(6, 0, -1):
                    remainder = order / (a + remainder)
                tail = (x / (a + remainder)) * asctile.exp((-0.5 * a) * a) * 0.3989422804014327
                out = asctile.where(x < -3.0, tail, out)
        asctile.copy_out(out.to(raw.dtype), out_gm, [offset], real_shape=[valid])


def gelu(x: torch.Tensor, approximate: str = 'none') -> torch.Tensor:
    if approximate not in ('none', 'tanh'):
        raise ValueError("approximate must be 'none' or 'tanh'")
    ensure_npu_platform()
    x = x.contiguous()
    y = torch.empty_like(x)
    size = x.numel()
    tile, unroll, vf = geometry(x.dtype == torch.float32, approximate)
    if size:
        cores = min(72, (size + tile - 1) // tile)
        gelu_kernel[cores](x.reshape(-1), y.reshape(-1), size, tile, unroll,
                           approximate == 'tanh', approximate == 'none' and x.dtype == torch.float32,
                           reuse_alloc=1, static_alloc=None, vf_fusion=vf,
                           insert_sync=True, opt_level=3, debug=False)
    return y
```

<a id="conclusions"></a>
## Итоговые выводы

1. **Официальная точность достигнута во всех пяти суточных jobs: 100/100 cases.** Два предыдущих контроля тоже 20/20. Для inline остаётся отдельно воспроизводимый локальный FP32 stress failure, поэтому полный диапазон точности не считается закрытым.
2. **Лучший наблюдаемый высокоуровневый вариант — balanced3840, GM 0,4160× reference.** Это лишь около 3,09% общего улучшения относительно baseline5120; FP32 exact улучшился на 9,63% по отношению времён baseline/new. Для общего 1× нужно ещё примерно 2,40× ускорения в терминах геометрического среднего. Порог 1× пересекает только case5, FP32 tanh [8192,8192].
3. **Высокоуровневая геометрия даёт измеримый, но небольшой резерв.** Переход [5120]/u1 → [3840]/u2 улучшил FP32 exact примерно на 8,53%; balanced-разбиение дополнительно изменило общую задержку примерно на 1,14%. Без повторов на одном контролируемом устройстве малые различия нельзя считать устойчивыми.
4. **64 AIV workgroups не стали универсально лучше 72.** Общий GM немного ухудшился, tanh улучшился, FP32 exact ухудшился. API score ранжирует c64 выше, но независимый GM reference/new — ниже balanced3840. Оба показателя раскрыты, выбор метрики не скрыт.
5. **Заполнение UB само по себе не объясняет скорость.** FP32 exact с 240 KiB дал умеренный выигрыш; inline с 60 KiB прошёл official accuracy, но плохие timings пришлись на другой runner. Сравнение разных математических маршрутов/runner не доказывает причинную связь UB и performance. Увеличивать UB искусственно не следует.
6. **Аппаратные выводы о JIT и Erf сейчас ограничены окружением.** Оба run на multi #2 медленнее host2 по неизменённому tanh примерно в 15 раз; между собой tanh почти совпадает. Это сильный контрольный признак возможного влияния runner/условий, но не установленная причина и не основание обвинять сервис. Нельзя заключить, что reuse_alloc=2, VF=false или Erf SUBSECTION сами по себе плохи.
7. **Erf-гипотеза частично подтверждена:** primitive локально точнее, official GeLU 20/20. В сравнении двух запусков на одинаково названном multi #2 inline FP32 exact быстрее JIT-варианта в 1,2266×; однако меняются сразу математика, тайлинг и JIT, и повторов нет. Изолированный hardware-выигрыш выбора ErfConfig пока не доказан; глобальный production FP32 stress ещё не пройден.
8. **Следующий обоснованный эксперимент, не выполненный этим отчётом:** проверить условия runner и повторить unchanged baseline/сравниваемый вариант на одном контролируемом окружении; затем отдельно варьировать ErfConfig, JIT и геометрию. Сохранить tanh как неизменённый контроль, стресс-тест FP32 и бюджеты UB/синхронизации. Новые credits требуют отдельной авторизации.
9. **Не доказано, что изменение compiler passes — единственный путь.** Есть эффект tile/unroll и математического выбора, но агрегированного 1× пока нет; аномалия runner мешает достоверно оценить JIT/inline. Прежде чем предлагать compiler fix, требуется matched-окружение, минимальная репродукция и атрибуция конкретному преобразованию. В этой серии компилятор не менялся.
