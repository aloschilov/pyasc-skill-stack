work — not that the agent workflow does.

## The case

`add`, float32, shape `[1000]`, tile 128, 1 block. 1000 = 7 x 128 + 104, so the
final tile is a 104-element tail. Tails are handled the way the skills document
them: allocate a full physical tile, pass the logical extent through
`real_shape`, and pad with the operation-neutral value 0.

Result: `max_abs_err = 0.0` against `x + y` in numpy. The tail region `[896,
1000)` is asserted separately so a kernel that silently skipped it could not
pass.

Reproducibility: four consecutive clean-cache runs, all exact.

## One unexplained failure

The very first simulator execution segfaulted (exit 139) before writing a
result. It has not recurred in four subsequent runs with cleared caches.

It was not the environment and not the kernel:

- the official `runtime-smoke.py` passes in this same venv and path;
- the construct was bisected into four variants — loop without tail, `real_shape`
  without loop, loop with constant `real_shape`, and loop with per-iteration
  `min()` `real_shape` — and all four pass, including the exact idiom that
  crashed;
- `ulimit -n` is 1048576, so this is not the simulator file-descriptor
  exhaustion the README warns about.

Recorded rather than explained. If it reappears it is worth pursuing; a single
unreproducible segfault is not enough to call the numerical gate flaky, but it
is also not something to leave undocumented.

## What this does not establish

One operator, one dtype, one shape, one block count, on a simulator. It is not
a numerical suite, not hardware qualification, and not a performance result.
The agent-generation path is untested because it is blocked upstream.
