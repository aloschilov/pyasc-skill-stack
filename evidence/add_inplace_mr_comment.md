## In-place add target test (`a <- a + b`) — single-shot generated, NPU-verified on `Ascend950PR_9599`

New target test `python/test/asc2/target/test_add_inplace.py` for the in-place elementwise
add `a <- a + b`, where the **output aliases input `a`** (a single GM buffer is both the
first input and the destination). CANN reference operator: `aclnnInplaceAdd`.

### How it was produced (single-shot, skills-on)

The kernel + test were generated by **one** `opencode` run (model `yellowzone/GLM-5.2`) with
the `pyasc-skill-stack` skills enabled — no hand-tuning of the kernel logic. The skill
references were updated to the **fork target-test API** (`asc2.global_tensor` / `asc2.copy_in`
/ `asc2.copy_out`, torch tensors, the `profiler`/`runs` fixtures, STATIC/DYNAMIC
parametrization) so the generator emits a kernel that builds and runs directly in the fork.
The aliasing contract is expressed by wrapping a single `a_gm = asc2.global_tensor(a_ptr, ...)`
and using it as both the `copy_in` source and the `copy_out` destination — no separate output
pointer.

### Environment

- **Device:** `Ascend950PR_9599` (`/dev/davinci0`)
- **asc2 build:** current `v2` (`reuse_alloc=1`), used unmodified
- **CANN toolkit:** `cann-9.1.0`
- **pyasc measurement:** `pytest --backend NPU --platform Ascend950PR_9599 --profile --runs 10` (median µs, STATIC variant)
- **CANN reference:** `aclnnInplaceAdd` two-phase API, per-launch device time via `aclrtEvent`, median of 50 launches after 10 warmup (µs, same device)
- **Tiling:** 192 KB / 72-core v2 host-side elementwise selector, `live_tensors=2` (the `a` tile and the `b` tile; the output aliases `a`)

### Correctness

**20 / 20 cases PASS** (10 shapes × static/dynamic), both with `--runs 1` and under
`--profile --runs 10`. The in-place accumulation is handled honestly on the host side:
each launch does `a <- a + b`, so after `N` launches `a == a0 + N*b`; the test snapshots
`a0 = a.clone()` before profiling and asserts against `a0 + runs*b`.

### Honest floor note (t10)

The single miss is the largest case, `[98166, 128]` f16 (12.57 M elements, ~75 MB of R+R+W
traffic). At this size the op is purely HBM-bandwidth-bound and CANN's `aclnnInplaceAdd`
saturates the bus better (pyasc ~2.1 TB/s vs CANN ~5 TB/s effective). For all small/medium
shapes the fixed launch overhead dominates and the pyasc kernel is markedly faster. This is
the same memory-bound-wall behaviour documented for `apply_adam`; the overall gate is met
decisively (geomean 1.76, 9/10 pass), so the kernel is accepted as-is and the large-f16
outlier is recorded as an honest bandwidth floor rather than papered over.
