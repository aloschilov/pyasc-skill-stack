# Lowering diagnosis: stock AscTile GELU at adadd7d6

The earliest concrete missed optimization in the candidate's fused arithmetic is **FindVFGroup's construction of dstList**, not a missing EliminateDataTransfer pass. It declares every arithmetic destination to be a group output, including values never read outside the group. EliminateDataTransfer subsequently forwards their loads but retains their final stores because they are declared outputs. This also keeps their UB allocations and buffer synchronization visible in final AscIR.

Separately, **LowerMath chooses the LocalTensor library ABI for erf**. That creates a real boundary in this AscTile pipeline: Erf is excluded from FindVFGroup and has no LowerToReg conversion. Its input/output transfers are required by that chosen ABI; the dead stores inside the following arithmetic group are not.

These are demonstrated compiler-stage limitations. They do not establish actual device traffic, a hardware speedup, or the cause of the slow model run. The independent dense FP32 numerical failure remains a submission blocker.

## Where the change first appears

Public [asctile.erf](https://gitcode.com/compiler-team/pyasc/blob/adadd7d66ed0ee16d33d79487bf584899a26ef1e/python/asctile/language/unary_ops.py#L205) builds `math.erf`. The [frontend IR](evidence/lowering-f32-none-r0-vf1/diagnostic/codegen.mlir#L27) still expresses `x * (erf(x*k)+1)*0.5` in tensor SSA. The initial tensor-to-LocalTensor lowering is not itself proof of redundant transfers: it is the representation consumed by the subsequent register optimizer.

[LowerMath.cpp:38–46](https://gitcode.com/compiler-team/pyasc/blob/adadd7d66ed0ee16d33d79487bf584899a26ef1e/lib/Conversion/LowerToAsc/LowerMath.cpp#L38) allocates a destination, supplies **no sharedTmpBuffer**, and supplies `isReuseSource=false`; [line 83](https://gitcode.com/compiler-team/pyasc/blob/adadd7d66ed0ee16d33d79487bf584899a26ef1e/lib/Conversion/LowerToAsc/LowerMath.cpp#L83) selects this conversion for `math.erf`. The same pass maps `abs` and `exp` to L2 operations at lines 89–92, which can enter VF groups. [Common.h:158](https://gitcode.com/compiler-team/pyasc/blob/adadd7d66ed0ee16d33d79487bf584899a26ef1e/lib/Conversion/LowerToAsc/Common.h#L158) shows that these destinations are initially LocalTensorAuto allocations.

Allocation hoisting precedes VF grouping: [compiler.py:131–156](https://gitcode.com/compiler-team/pyasc/blob/adadd7d66ed0ee16d33d79487bf584899a26ef1e/python/asctile/runtime/compiler.py#L131) schedules reuse1 before and after hoisting, or reuse2 after hoisting, followed by FindVFGroup, LowerToReg, loop fusion, and DispatchHoist. For this C310 loop, all eligible allocations are hoisted out of the tile loop, as shown before/after [HoistTensorAllocation](evidence/lowering-f32-none-r0-vf1/stdout.log#L2922) / [RefineCubePosition](evidence/lowering-f32-none-r0-vf1/stdout.log#L2992). Six allocations remain for FP32/reuse0. Hoisting enables adjacent arithmetic to group; it does not by itself require an intermediate value to escape a VF group.

The decisive mistake is in [getOutputLocalTensors](https://gitcode.com/compiler-team/pyasc/blob/adadd7d66ed0ee16d33d79487bf584899a26ef1e/lib/Dialect/AscVF/Transforms/FindVFGroup.cpp#L175): it appends every compute destination and only deduplicates the list. It never asks whether a value will be read after the group. [wrapInVFGroupOp](https://gitcode.com/compiler-team/pyasc/blob/adadd7d66ed0ee16d33d79487bf584899a26ef1e/lib/Dialect/AscVF/Transforms/FindVFGroup.cpp#L189) installs that list as dstList. [VFGroup's declaration](https://gitcode.com/compiler-team/pyasc/blob/adadd7d66ed0ee16d33d79487bf584899a26ef1e/include/ascir/Dialect/AscVF/IR/Ops.td#L47) makes these ordinary operands, so they also keep references to the allocations alive.

Concrete FP32/reuse0 trace: immediately [before FindVFGroup](evidence/lowering-f32-none-r0-vf1/stdout.log#L3208), the tail writes `%6 = erf_result+1`, `%5 = x*%6`, `%4 = %5*0.5`. Only `%4` feeds copy-out. Immediately [after FindVFGroup / before LowerToReg](evidence/lowering-f32-none-r0-vf1/stdout.log#L3280), the group nevertheless declares `dstList=[%6,%5,%4]`, `srcList=[%9,%7]`, using operand segments `[3,2,1]`. This is the first explicit false escape boundary for those two intermediate results.

Erf itself is not grouped because [isFusible](https://gitcode.com/compiler-team/pyasc/blob/adadd7d66ed0ee16d33d79487bf584899a26ef1e/lib/Dialect/AscVF/Transforms/FindVFGroup.cpp#L43) enumerates L2 arithmetic, excludes Erf, Cast, CompareScalar and Select, and [findGroupsImpl](https://gitcode.com/compiler-team/pyasc/blob/adadd7d66ed0ee16d33d79487bf584899a26ef1e/lib/Dialect/AscVF/Transforms/FindVFGroup.cpp#L106) closes a group on every other operation. [Singleton groups are discarded](https://gitcode.com/compiler-team/pyasc/blob/adadd7d66ed0ee16d33d79487bf584899a26ef1e/lib/Dialect/AscVF/Transforms/FindVFGroup.cpp#L132). Thus the single scale before Erf stays an L2 call and the three operations after Erf become one VF group. BF16/FP16 casts remain outside it.

## Required versus redundant UB traffic and allocations

These are static transfer **sites inside AscTile VF groups**, before Bisheng optimization. At tile=1024, FP32 vector length=256 bytes, each such site runs over 16 chunks of 64 floats: one full-tile store site represents 4096 bytes in the generated loop. These counts exclude GM↔UB DMA, casts, the library's own loads/stores, and scalar padding code.

| Mode, all three dtypes | VF groups | Register loads r0/r1/r2 | Stores r0/r1/r2 | Stores required by existing group boundaries | Redundant stores r0/r1/r2 |
| --- | ---: | --- | --- | ---: | --- |
| Exact/public erf | 1 | 2 / 2 / 2 | 3 / 2 / 1 | 1 | 2 / 1 / 0 |
| Stable tanh-exp | 2 | 3 / 3 / 3 | 12 / 6 / 4 | 3 | 9 / 3 / 1 |

**Exact:** the fused tail must read `x` and `erf(x*k)`, and store final `y` for copy-out (or final dtype cast). In [reuse0 final IR](evidence/lowering-f32-none-r0-vf1/diagnostic/ascir.mlir#L108), stores at lines 111 and 116 write `erf_result+1` and `x*(erf_result+1)`; the following math consumes the registers directly, and only the third store at line 119 feeds copy-out. The two intermediates have no subsequent reader outside the group. They also retain two separate 4096-byte allocations, hence 8192 bytes of avoidable materialized temporary capacity in this IR if dead-output cleanup is implemented.

[Reuse1](evidence/lowering-f32-none-r1-vf1/diagnostic/ascir.mlir#L101) writes an intermediate product back into the old Erf-result allocation at line 106 and final y into another at line 109. The intermediate has no outside consumer. [Reuse2](evidence/lowering-f32-none-r2-vf1/stdout.log#L4158) maps the whole tail to the same destination, so overwrite elimination removes both earlier stores and leaves only final y. This is why reuse2 improves transfer count even when reuse1 and reuse2 report the same UB footprint.

These reuse modes run before VF formation; they are not register-allocation levels. [Legacy reuse](https://gitcode.com/compiler-team/pyasc/blob/adadd7d66ed0ee16d33d79487bf584899a26ef1e/lib/Dialect/Asc/Transforms/ReuseUBAllocation.cpp#L181) replaces allocation uses with reinterpreted earlier storage; [experimental reuse](https://gitcode.com/compiler-team/pyasc/blob/adadd7d66ed0ee16d33d79487bf584899a26ef1e/lib/Dialect/Asc/Transforms/ReuseTensorAllocation.cpp#L209) checks allocation lifetimes and reusable-source interfaces, then colors conflicting allocations. Their different physical destination identities feed the later overwrite-store rule. They do not repair dstList's definition.

**Stable tanh-exp:** [first group](evidence/lowering-f32-tanh-r0-vf1/diagnostic/ascir.mlir#L94) computes `e=exp(-abs(t))`; only e must escape it. The [CompareScalar at line 168](evidence/lowering-f32-tanh-r0-vf1/diagnostic/ascir.mlir#L168), which produces the sign predicate, splits this group from the branch arithmetic. The [second group](evidence/lowering-f32-tanh-r0-vf1/diagnostic/ascir.mlir#L177) must load x and e and export both branch results for [Select at line 228](evidence/lowering-f32-tanh-r0-vf1/diagnostic/ascir.mlir#L228). Its denominator `e+1` and numerator `x*e` are internal. Thus reuse0 has seven dead stores in group 1 and two in group 2. Reuse1 leaves a dead `-abs(t)` store ([line 116](evidence/lowering-f32-tanh-r1-vf1/diagnostic/ascir.mlir#L116)) and two dead stores in group 2. Reuse2 still spills the denominator ([line 154](evidence/lowering-f32-tanh-r2-vf1/diagnostic/ascir.mlir#L151)). Eliminating all nine reuse0 spills corresponds to 36864 bytes of generated UB writes per full tile; this is an IR calculation, not measured bandwidth.

The e round-trip and two branch-result stores are necessary with these two groups plus an external Select. A compiler implementation with register Compare/Select fusion could avoid more, but that is a separate proposed change. Likewise, the scaled Erf input and Erf output are materialized because of the chosen library ABI, not because they are dead VF temporaries.

**Arithmetic control, no erf:** `reproducer.simple` computes `x*x+x*0.25`. Reuse1 and reuse2 both show [one load, two stores](evidence/lowering-simple-r1-vf1-v2/diagnostic/ascir.mlir#L72); only final y is needed outside the group, so the x*x store at line 75 reproduces the false-output issue without a library math operation. UB is 8192 for both modes.

An additional grouping limitation appears with this control's reuse0: [allocations remain interleaved with its three arithmetic operations](evidence/lowering-simple-r0-vf1-v2/stdout.log#L2141), so it produces **zero VF groups**, UB=16384. Unlike the candidate it has no enclosing tile loop. [HoistOpPattern:32–34](https://gitcode.com/compiler-team/pyasc/blob/adadd7d66ed0ee16d33d79487bf584899a26ef1e/include/ascir/Dialect/Asc/Utils/Utils.h#L32) stops at a function parent, and FindVFGroup treats each intervening allocation as a group separator. This is a reproducible allocation-placement limitation; it must not be generalized to claim that all simple arithmetic fuses under reuse0.

Required integration rule for the main tuning harness, **before any simulation**:

1. Compile with the stock compile-only path; retain result/artifact SHA and effective configuration. A compile or sync-verification failure is ineligible.
2. If UB metadata exists, compare it with 253952. Prune an overflow immediately; compilation success alone does not establish capacity.
3. If UB metadata is absent or `{}`, use a complete constant TPipe reservation accounting where supported. An explicit subtotal above capacity proves overflow. Unresolved/dynamic/control-flow-dependent allocation, unrecognized storage, or unaccounted internal scratch remains **unknown, not fit**.
4. A subtotal within capacity establishes only that the accounted buffers fit. TPipe's dynamic base and any backend/internal allocation must also be accounted for before claiming total runtime fit. Keep numerical eligibility separate.
5. Recompile each tile/unroll configuration: do not scale these tile1024 measurements blindly. For example, the measured FP32/tanh/reuse0 allocation shapes imply 14×tile×4 plus a tile/8 predicate buffer (32-byte aligned); tile8192 would already require 459776 explicit bytes and must be pruned if a stock compile reports that layout. This example is derived, not an additional measured run.

The analyzer reports `ub_explicit_bytes`, an accounting scope, unknown reasons, and `ub_prune_decision`; it deliberately never sets `total_runtime_ub_fit_proven` true. It does not modify or launch the main gate.

It does not read/write a scratch UB array. [CheckTensorPos](/usr/local/Ascend/cann-9.0.0/aarch64-linux/asc/impl/basic_api/kernel_check.h:340) inspects position only in CPU-debug builds.
6. The default [ErfConfig](/usr/local/Ascend/cann-9.0.0/aarch64-linux/asc/include/adv_api/math/erf_utils.h:25) is PADE_APPROXIMATION. [ErfPadeCompute](/usr/local/Ascend/cann-9.0.0/aarch64-linux/asc/impl/adv_api/detail/math/erf/erf_c310_impl.h:104) uses register temporaries for clipped P/Q evaluation. The mere inclusion of kernel_pop_stack_buffer.h is not evidence that this computation spills intermediates to scratch.

**Conclusion:** a no-scratch wrapper and a TPipe-based scratch *descriptor* are proven. Actual UB0 aliasing is unresolved; scratch-induced data clobbering is unsupported by the selected C310 computation, which does not access that descriptor's storage. No extra physical scratch-byte total or scratch-related sync count can be assigned from this path. TPipe/wrapper setup may have cost if it survives backend optimization, but attributing the extremely slow model run to that cost is a **hypothesis**, not a finding. The Broadcast-only exclusion in DispatchAlloc is not enough to conclude that Erf needs the same exclusion.

## Synchronization and backend limits

The stock schedule [inserts C310 buffer-ID synchronization and verifies it](https://gitcode.com/compiler-team/pyasc/blob/adadd7d66ed0ee16d33d79487bf584899a26ef1e/python/asctile/runtime/compiler.py#L165) after VF and allocation passes. [InsertBufIdSync:172–195](https://gitcode.com/compiler-team/pyasc/blob/adadd7d66ed0ee16d33d79487bf584899a26ef1e/lib/Dialect/Asc/Transforms/InsertBufIdSync.cpp#L172) explicitly visits both dstList and srcList for each VF group. Overdeclared outputs therefore also produce overconservative group buffer coverage. For example, [exact/reuse0](evidence/lowering-f32-none-r0-vf1/diagnostic/ascir.mlir#L80) acquires/releases five distinct buffers around the tail; two correspond to the two dead intermediates. The necessary input/output ordering must remain when those intermediates are removed.

For FP32/exact, total static get_buf/rls_buf **pairs of sites**, reuse0/1/2, are 14/12/11 without VF and 12/10/9 with VF. For FP32/tanh they are 37/27/23 and 24/16/14. These include the conditional padding path; they are not dynamic event counts or a timing model. All 108 sync-verification passes succeeded.

[InsertLocalMemBar](https://gitcode.com/compiler-team/pyasc/blob/adadd7d66ed0ee16d33d79487bf584899a26ef1e/lib/Dialect/AscVF/Transforms/InsertLocalMemBar.cpp#L31) inserts store→load barriers between successive VFFor loops within each group. After fusion each candidate group has only one VFFor, so **no local_mem_bar** survives in these matrix artifacts. That absence is expected and does not establish a missing synchronization bug.

Bisheng then receives [--cce-auto-sync](https://gitcode.com/compiler-team/pyasc/blob/adadd7d66ed0ee16d33d79487bf584899a26ef1e/python/asc/runtime/compiler.py#L373) and can further optimize the C++ and inline library calls. The exact/reuse1 [object symbol table](evidence/lowering-f32-none-r1-vf1/binary.symbols.txt) contains a combined vector-thread name including Muls, ErfCoreImpl and gelu_kernel, suggesting further backend fusion. The installed objdump's [disassembly attempt](evidence/lowering-f32-none-r1-vf1/binary.disasm.txt) returns `<not available>` for C310 instructions. Consequently this report proves redundant transfers and allocations **at AscIR/C++**, and cannot claim that every such store reaches machine code or dominates simulator time.

## Numerical/API status is independent

[smoke2-exact-f32/result.json](evidence/smoke2-exact-f32/result.json) records `numerical_passed=false` for 4097 adversarial points over [-10,10]: MERE=0.020366391951169845 and MARE=3.4659441066804635. Its later `current_tick` AttributeError belongs to the old timing harness; it does not explain or invalidate the already recorded numerical failure. The [reduced smoke summary](evidence/numerical-smoke/summary.json) passes 6/6, which is weaker coverage.

The new dense matrix is complete: **0/18 exact-mode flag configurations passed** the mandatory FP32 negative-tail check, all under the current candidate SHA. The [reuse0/default/VF=false](evidence/numerical-dense-exact/float32-none-r0-sdefault-vf0/result.json), [VF=true](evidence/numerical-dense-exact/float32-none-r0-sdefault-vf1/result.json), and [static=false/VF=false](evidence/numerical-dense-exact/float32-none-r0-sfalse-vf0/result.json) saved actual-output arrays were additionally compared and are elementwise identical. The failure is not repaired by any reuse/static/VF setting in this matrix.

The main task's [measured API reproducer](evidence/numeric-reproducer.json) now isolates a concrete cause at x=-4.111328125, z=-2.9071478843688965: CANN Erf returns -0.9999605417251587, while correctly rounded FP32 Erf is -0.9999606609344482, a **two-ULP error**. The resulting GELU is -8.111295755952597e-5 versus float64 golden -8.086769955458579e-5; the official checker gives MARE=0.003029084196911871, 64/64 mismatches and 64 cancellation failures, versus zero CPU cancellation failures.

Crucially, the correctly rounded Erf path gives -8.086790330708027e-5, exactly the CPU result at this point. Thus this is demonstrated **public CANN Erf accuracy error amplified by 1+erf cancellation**; it is not evidence that every FP32 implementation or FP32 quantization must fail here. This API/numerical limitation is distinct from the redundant VF-store issue and from JIT option propagation. The diagnostic task only read the main task's numerical evidence; it did not add a simulation.

Compile/sync success, reduced smoke success, UB accounting, and numerical eligibility are four separate facts. Full geometry promotion/submission remains blocked by the failed mandatory exact gate. The main task's finite warmed performance controls can quantify a limited workload but cannot remove that blocker. The separate x86 build remains outside this lowering diagnosis.

**Confidence:** high for the false VF output boundary, surviving IR stores, option/memory comparisons, and the isolated API accuracy failure (direct source, stage IR and measured evidence). High for the C310 Erf source path not consuming scratch storage. Actual PopStackBuffer UB0 aliasing, surviving backend store instructions, runtime synchronization cost and the cause of the slow model run remain unproven; no compiler patch or performance improvement is claimed.

## Actionable compiler changes, not implemented here

1. Fix the output definition at **FindVFGroup.cpp:175–197**: compute which final memory values are read outside/after the group, with alias and loop liveness, rather than exposing all arithmetic destinations. Earlier users of a reused allocation do not mean its current contents escape. Let the existing EliminateDataTransfer remove the newly non-output stores; update group operand lists and remove allocations that become dead.
2. Add regression cases for these observed contracts: exact tail r0=2 loads/1 required store; arithmetic control r1/r2=1 load/1 store; stable tanh's current split groups=3 loads/3 required stores. These are proposed pass-level expectations; revalidate sync, masking, aliases and multiple iterations in an actual compiler change.
3. Address the separate adjacency limitation: allocation ops interleaved with simple top-level arithmetic should not accidentally turn a fusible chain into discarded singleton groups. The no-loop reuse0 control is the minimal observed case.
4. A C310 register-capable Erf lowering would address the earlier library-ABI boundary; **merely adding Erf to isFusible is insufficient** because LowerToReg also needs a compatible conversion. Preserve public numerical semantics and resolve the dense checker failure independently. Compare/Select/Cast fusion requires its own lowering support too.
5. In the main compile gate, apply explicit capacity pruning before launching and preserve unknown TPipe accounting. Keep compiler/performance findings available even while exact-mode numerical eligibility is blocked.
